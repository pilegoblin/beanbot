# Speech, and a per-Medium budget on the Capabilities that cost money

BeanBot can be asked to say something out loud. A `generate_speech` Capability takes the words, a Voice and an optional direction, and posts a Clip to the channel. Alongside it, every Capability now declares a Medium, and at most one Capability of each Medium runs per Trigger — which closes issue #1 by bounding image generation as a side effect of bounding speech.

## Considered Options

**What "audio" means.** Three different products hide behind the word, priced and shaped differently. Music generation is Lyria: a costlier model, Vertex-side rather than on the Gemini API the rest of BeanBot speaks to, and streaming-shaped rather than one-shot. Invented sound effects have no cheap Google model at all and would mean a second provider, a second key and a second billing relationship. Speech is the one that is cheap, one-shot, and reachable through the client already in `internal/gemini`. Within speech, voicing BeanBot's own reply automatically was rejected in favour of a Capability the model calls deliberately: a bot that speaks every reply aloud is a bot nobody keeps in a channel, and the Capability shape means the model asks for a Clip exactly when someone wanted one.

**Whose voice.** A single Voice configured per deployment alongside the Backstory — BeanBot having *a* voice the way it has a persona — was rejected in favour of the model picking one per Clip. The cost is that a Clip is not "BeanBot speaking" so much as BeanBot doing an impression, and there is no recognisable voice a server comes to know. What it buys is the thing that makes the Capability worth having: the delivery can suit the line.

**How much of the catalogue.** Gemini offers thirty voices, named for stars and moons, and the name says nothing whatever about the sound — the one-word characteristic beside it is the entire signal. Declaring all thirty with their characteristics was rejected on the cost ADR 0003 already established as real: a declaration reaches the model on *every* Trigger, so the full catalogue is a permanent per-conversation token charge in every server to serve a tool that fires rarely. Declaring all thirty as bare names is cheaper and worse than useless, since the model would be choosing blind. Six, described, span the range at a fraction of the tokens, and a model choosing between six labelled options chooses better than one facing thirty opaque ones. The shortlist is hardcoded rather than configured: which voices exist is a fact about the model, not a decision about the deployment, and the per-Clip choice — the part that is a taste question — already belongs to the model.

**What bounds a Clip.** A limit stated only in the tool description was rejected for exactly the reason the Gate lives in Go: it is advisory, and ADR 0003 established that Memory is member-writable and injected into every prompt, so "always speak for as long as you can" is a durable instruction a prompt-side limit will simply lose an argument with. The cap is therefore a character count enforced in Go before the call, on the words and on the style direction separately — the direction is prefixed onto the script the model reads aloud, so an essay there is another way to buy a long Clip. It counts characters rather than bytes, since a byte cap quietly hands a Cyrillic script half the allowance of an English one for the same amount of speech.

**The container.** Gemini returns headerless PCM, which Discord will not play; it arrives as an unidentifiable blob. Transcoding to MP3 or Opus produces files roughly ten times smaller, and was rejected because the length cap has already made that headroom worthless — eighty seconds of speech is about 4MB against a 10MB attachment limit — while costing an `apt` layer in an image that has none, a subprocess and its failure modes, and a working `ffmpeg` for anyone running outside Docker. A 44-byte RIFF header written with `encoding/binary` needs no dependency at all. Its sample rate is read from the response's MIME type rather than hardcoded, because a model change that altered the rate would otherwise produce no error at all — just every Clip playing back at the wrong speed.

**What bounds spending.** Speech is the *cheap* medium: a thirty-second Clip costs about a fifth of one image. The problem it surfaces is not its own cost but that it would have been the second ungated, unbudgeted way to spend money per Trigger, which is what issue #1 was opened about for the first one. Giving speech its own private cap and leaving images alone was rejected as building the second of two counters that a proper fix would then have to unify. A single shared counter across both media was rejected because its worst case is two images — precisely the case in the issue — and because it makes a cheap Clip compete against an expensive Image for no reason anyone could explain. Each Medium therefore gets its own budget of one. Reusing `Mutating()` to borrow the existing one-per-Trigger budget was tempting and wrong: a Clip changes nothing in the Guild, so it would corrupt the word, and it would break "make the event and say it out loud".

**How long a budget lasts.** Issue #1 asks whether the bound should also be per-Guild-per-hour, and it is deliberately not. A rate limit needs state that outlives a Trigger, and BeanBot has exactly one place to keep such a thing — a volume bound to a single machine, which a deploy interrupts — so the choice is between inventing durable spend-tracking and keeping a counter that silently resets. But the stronger reason is that the two exposures are not the same shape. A planted Memory is one act by one member that recurs invisibly on every later Trigger, and the per-Trigger budget kills it outright. Fifty messages in a row is fifty deliberate acts, in the channel, under the member's own name, against a bot that only ever answers when spoken to — which is a moderation problem, and Discord already has the tools for it. A rate limit would buy protection against the loud case at the cost of throttling a busy server, and can be added the day someone actually does it.

**Safety.** `permissiveSafety()` applies, as it does everywhere else. A realistic voice saying attacker-chosen words about a named member is a genuinely different artifact from the same words typed, which is the argument for leaving the filters on here alone. It was rejected because the words reaching the speech model were produced by a model whose filters are already off, so the second filter blocks nothing new and buys only mid-persona refusals on text BeanBot was about to say anyway.

## Consequences

- Issue #1's suggested shape — a per-Trigger budget threaded through `agent.run` alongside `mutated`, refusing further calls once spent and reporting the refusal back to the model — is delivered here as a side effect rather than by a change aimed at it. `generate_image` and `edit_image` share the image Medium, being the same call to the same model at the same price, so redrawing repeatedly, the cheapest way to spend a lot, is bounded too. The second question that issue raises, a per-Guild-per-hour limit, is answered *no* above and not implemented; fifty messages still buy fifty images.
- The budget is spent on success, not on attempt, matching what `Mutating()` already did: a Clip refused for an overlong script must leave room for the model to retry with a shorter one in the same Trigger.
- `Capability` grew a method, so all six existing Capabilities had to declare a Medium. Most declare `NoMedium`, which is the honest answer and the zero value.
- Every refusal names the Medium it ran out of, because the model's only account of why nothing came back is the string it gets to relay to the channel. It also tells the model not to try again in this turn, rather than borrowing the existing mutation refusal's "ask again for the next one" — that phrasing is read *inside* a turn with round-trips still to spend, and an invitation spends them all on calls that will be refused identically.
- Nothing new is configurable. There is no way to disable speech, no way to change the shortlist, and no way to move off the model without a deploy — and `gemini-2.5-flash-preview-tts` is a preview model, chosen deliberately for being half the price of the alternatives. A withdrawal is a code change. This is the same trade already made for Nano Banana.
- The Voice names are documentation-only strings that appear in no SDK constant, so nothing in the type system notices if one is retired or renamed. The live smoke test speaks once in every voice on the shortlist, which is the only place that check exists.
- The eighty-second cap is not a cost control — at these prices it would take a two-and-a-half-minute Clip to match a single image. It bounds attention span and attachment size.
